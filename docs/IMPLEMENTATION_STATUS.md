Entries distinguish code presence from end-to-end verification; dated evidence names the exact tested commit.

## Status definitions

- **Implemented and verified:** the real workflow was exercised with the required runtime and evidence is recorded.
- **Implemented, CI-verified:** compiled and covered by automated tests in GitHub Actions (unit tests with real temporary files, typecheck, lint, build). The workflow has NOT been exercised in a running desktop app unless a row says so.
- **Implemented but not yet verified:** the workflow is connected in code, but its required desktop runtime, account, provider, or installer test has not completed.
- **Partially implemented:** useful real functionality exists, but listed gaps remain.
- **Not implemented:** no working product workflow exists.
- **Blocked by an external dependency:** completion needs identified credentials, provider capabilities, signing material, or hardware.

## Server-world operations

- **Stopping is not deleting.** Stop ends the process. Deleting is separate, typed-confirmation, and limited to the items named above.
- **Cancellation by phase.** Backup: cancellable while scanning, copying and writing the manifest; not cancellable during the final rename. Verify: always cancellable, read-only. Restore: cancellable while verifying and copying; not cancellable during the final rename. Delete: not cancellable, because stopping halfway would leave a half-deleted world.
- **Known limits.** Progress is per phase (bytes and files), not one blended percentage. A world modified by an external process during a copy can make done exceed total; the UI clamps to 100%. Another process holding the world open cannot be detected beyond the port probe, so keep Minecraft closed. Deletion is permanent and does not use the recycle bin. Windows file locking and read-only attributes are handled only by a single retry; failures are reported as partial deletion.

**Pairing failure and workaround.** The earlier streaming attempt, validation run [#166](https://github.com/Shubhajitro90/CloudCraft/actions/runs/40302078085) at `e2676949f183b4ddceed74cb781eff10119de55c`, failed in the streaming job; its uploaded artifact (ID `12641666237`) contains Moonlight's `Qt Critical: Incorrect PIN`. Moonlight `v6.2.0` source constructs the AES key from `QCryptographicHash::hash(...).constData()` and then truncates it to 16 bytes ([upstream source](https://github.com/moonlight-stream/moonlight-qt/blob/v6.2.0/app/backend/nvpairingmanager.cpp#L227-L231)). The C-string conversion can stop at an embedded NUL, leaving a short key and causing a valid PIN to be rejected; for random digest bytes, a NUL in the first 16 bytes has an estimated 6.1% probability. The log proves the rejection, while source inspection supports this code-level failure mode; the log alone cannot prove that this specific failed attempt was caused by that bug. Commit `bced67ea9f47112192b9520b1e9a37de6f1c50db` adds up to five pairing attempts with a fresh isolated Moonlight identity each time. The passing run succeeded on its first attempt. This is a bounded workaround, not an upstream Moonlight fix; repeated trials have not measured its failure rate.

**Certificate and rootfs scope.** CloudCraft's provider computes SHA-256 over the presented DER leaf certificate using Rust code, compares the resulting 32-byte digest with the configured pin, and rejects a mismatch; certificate probing sends no credentials. The provider file uses rustls and `sha2` and does not invoke the OpenSSL CLI. The loopback test script itself does use `openssl s_client` to obtain the test host's certificate fingerprint, and its CI job installs OpenSSL. No rootfs is tracked in this branch, and the workflow installs Sunshine on the Ubuntu 24.04 runner rather than building or entering a rootfs. Thus this evidence does not audit rootfs packages, permissions, sandboxing, or runtime compatibility.

## Reproducing the streaming test

`.github/scripts/sunshine-loopback-e2e.sh` starts Sunshine on one virtual display, pairs Moonlight with a random PIN through `GET`/`POST /api/pin` (this Sunshine version requires the pending `pairing_id`), and runs the opt-in test with Moonlight on a second display. It needs Ubuntu 24.04 with `xvfb pulseaudio mesa-utils x11-apps openssl`, the Sunshine `.deb`, and `CLOUDCRAFT_MOONLIGHT` set to the Moonlight ELF binary (for the AppImage, `--appimage-extract` and use `squashfs-root/usr/bin/moonlight`, not `AppRun`, so process-ownership checks see the real executable). Against your own remote host, run the test directly with the variables in its doc comment.

## Exact external dependencies still required

1. A legitimate Microsoft/Minecraft account, Java runtime, desktop OS, and game assets for authenticated local-launch integration testing.
2. Java and a legitimate Minecraft server JAR for an end-to-end local server start, join, graceful stop, and world-persistence test.

5. Platform signing identities, update signing keys, published release metadata, and physical/virtual installation environments for signed installer and updater acceptance.
